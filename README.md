# 面向智能客服场景的企业级 Agent 执行引擎（Agent Runtime）

> **场景**：电商智能客服。客服 Agent 替用户**查订单、查资料、发起退款、发通知、清理记录** ——
> 这些动作里既有只读查询，也有**一旦执行错就造成真实资金/数据损失**的写操作
> （退款扣两次、通知发错人、记录误删）。
>
> **定位**：解决"**Agent 敢不敢让它在客服场景动手**"这个问题。
> 让 Agent 能**安全地动手**（工具权限 + 高危审批 + 幂等 + 审计）、**挂了能恢复**（状态管理 + 约束控制 + 优雅收尾）、**能证明它行**（轨迹回放 + 任务级评测 + 失败归因）。

---

## 典型场景：一笔 3000 元退款工单是怎么走的

用户：「我这单要退款 3000 元」→ 客服 Agent 开始工作

| 阶段 | 发生了什么 |
|---|---|
| **THINKING** | 模型决定先查订单 → `query_order(ORD-000777)` |
| **ACTING** | ① 工具存在性 ✓ → ② 权限校验（客服专员可发起退款）✓ → ③ 参数校验（订单号格式、金额范围）✓ → ④ 计算幂等键 `hash(task_id + issue_refund + ORD-000777 + 3000)` → ⑤ **幂等检查**：这笔没做过，继续 → ⑥ **高危审批**：3000 > 500 → **挂起并生成审批单** ★ |
| **OBSERVING** | 把"已提交人工审批，请勿重复提交"回填给模型 |
| **THINKING** | 模型据此给出阶段性结论（**而不是重复提交**） |

**同一套机制在另外三种情况下分别拦住了什么**：

| 情况 | 哪一关拦住 | 结果 |
|---|---|---|
| Agent 重试同一笔退款 | ⑤ 幂等检查 | 返回首次结果，**不会扣两次钱** |
| 初级客服（只读角色）试图退款 | ② 权限校验 | 越权调用被拒，**且拒绝原因回填给模型**（否则它会一直重试同一个被拒的调用） |
| 模型幻觉出一个 `drop_database` | ① 工具存在性 | **直接拦住——因为它根本不在注册表里** |
| 模型在原地反复查同一单 | 运行时循环检测 | **4 步就中止**，并输出"已查到订单状态"的阶段性结论 |

> 以上每种情况都有对应的评测用例，见 `data/eval_tasks.jsonl`（10 条任务覆盖：正常查询 / 越权 / 大额审批 / 小额直通 / 循环 / 参数错误 / 超时 / 规划错误 / 违规陷阱）。

## 一、它解决什么问题

市面上多数 Agent 项目停在"ReAct + 几个工具 + 跑通 demo"。但企业里落地的真正障碍是另外三件事：

| 障碍 | 具体担忧 | 本项目的回答 |
|---|---|---|
| **敢不敢让它动手** | 它要是删了库、发错邮件、调错接口怎么办？ | 工具网关：权限白名单 + 参数强校验 + 高危审批 + 幂等 + 审计 |
| **挂了怎么办** | 跑 20 步崩了要从头来？重试会不会重复扣款？ | 状态机 + 三约束 + 幂等键 + 优雅收尾 + 轨迹落盘 |
| **怎么证明它行** | 非确定性系统怎么测？为什么这次失败了？ | 任务级评测 + **失败归因九分类**（告诉你该改哪一环） |

## 三、三个核心模块

### 1. 工具网关（`gateway.py`）

**核心前提：模型生成的工具调用是不可信的**——它可能越权、编造参数、重复调用、执行危险操作。所以不能让 Agent 直接调工具。

**8 步流水线**（顺序不可变）：

| 关卡 | 拦什么 | 对应风险 |
|---|---|---|
| ① 工具存在性 | 未注册的工具 | 模型幻觉出不存在的工具 |
| ② 权限校验 | 角色不在白名单 | 越权（普通用户借 Agent 之手删库） |
| ③ 参数校验 | Pydantic schema 不通过 | 幻觉参数 / SQL 注入串 |
| ④ 算幂等键 | `hash(task_id + 工具 + 规范化参数)` | 为下一步与审批去重做准备 |
| ⑤ **幂等检查** | 已执行过 → 返回首次结果 | **重试导致重复副作用**（重复退款/重复发消息） |
| ⑥ 高危审批 | 静态规则 + 动态规则 | 无人值守时的误操作 |
| ⑦ 沙箱执行 | 超时 / 异常隔离 | 单个工具挂死拖垮服务 |
| ⑧ 审计留痕 | —— | 合规要求：谁在何时改了什么 |

**三个设计要点**：

- **高危判断支持动态规则**：`send_email` 天生高危（静态）；`issue_refund` 则是"金额 > 500 才需审批"（动态）。只做静态的话，要么全部审批（人烦了会无脑点通过），要么全不审批（风险失控）。
- **幂等键必须带 `task_id`**：区分"同一任务的重试"（只执行一次）和"两个不同任务的相同业务"（各执行一次）。不带的话，第二笔真实业务会被当成重复而**被吞掉**。
- **审批单本身也要幂等**：按幂等键去重，否则 Agent 重试会创建一堆一模一样的待办。

### 2. Agent 运行时（`runtime.py`）

**为什么不用裸 ReAct**：

| 裸 ReAct 的问题 | 本项目的解法 |
|---|---|
| 路由漂移（模型自由决定下一步） | 流程固化成状态，模型只能在节点内决策 |
| 死循环（反复调同一个工具） | 重复调用检测（连续 N 次相同调用 → 判定卡死） |
| 成本失控 | `max_steps` + `token_budget` 双约束 |
| 挂了从头来 | 全量轨迹落盘（可回放） |
| 不可观测 | 每步记录思考/动作/观察/token/耗时 |

**关键设计：优雅收尾（不是直接失败）**

```
到达约束上限
  ❌ 直接报错 → 用户什么都拿不到
  ✅ 进入 FORCE_ANSWER → 基于已有观察产出阶段结论
```

测试证据：死循环场景 **4 步就中止**（上限 10 步），但**仍产出了收尾结论**。

**另一个细节**：收尾阶段必须换一个 brain（`ForceAnswerBrain`）——原 brain 不知道预算已耗尽，会继续要求调工具，导致收尾阶段又触发约束。

### 3. 任务评测 + 失败归因（`evaluation/`）

**归因九分类**（按严重程度排序，安全问题永远优先报）：

| 归因 | 含义 | 该改哪里 |
|---|---|---|
| POLICY_VIOLATION | 调用了禁止的工具 | 收紧权限白名单 + prompt 明确禁止项 |
| PERMISSION_DENIED | 越权尝试被拒 | 检查角色配置 / prompt 说明可用工具范围 |
| PARAMETER_ERROR | 参数被校验拦下 | 优化参数描述 + few-shot |
| ENVIRONMENT_ERROR | 工具超时/异常 | 排查下游稳定性 + 分类重试 |
| BUDGET_EXHAUSTED | token 耗尽 | 简化任务或提高预算 |
| LOOP_DETECTED | 陷入重复调用 | 观察里补中间结果提示 |
| MAX_STEPS | 步数超支 | 拆分任务 / 减少工具粒度 |
| NO_ACTION | 既不动手也不作答 | 检查工具描述清晰度 |
| PLANNING_ERROR | 期望工具没被调用 | 优化规划提示 |

**为什么用确定性规则（不调 LLM）**：归因本身必须**可靠、可复现、零成本**。LLM 归因适合做补充，不能做主力。

## 四、工程问题档案（本项目最有价值的部分）

以下 10 个坑。它们共同的特点是：**看起来对，边界场景下不对**。

**来源分三类**（面试时值得主动区分，因为这是三种不同的能力）：
开发中真实踩到 7 个（其中坑 2 是**设计阶段推演**出来的，不假装是被测试抓到的）、
**代码复审时发现 3 个**（坑 8、9、10，测试集里没有对应用例，不会自己冒出来）。

| # | 坑 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **假超时** | 写了 0.5s 超时，实际等 2s | `with ThreadPoolExecutor()` 退出时调用 `shutdown(wait=True)`，**阻塞等任务跑完** | 手动管理 executor + 超时后 `shutdown(wait=False, cancel_futures=True)` |
| 2 | **幂等键缺 task_id** | （设计阶段推演，非测试抓到） | 只用 `hash(工具+参数)` 会把两笔真实业务误判为重复 → **业务被吞** | 幂等键 = `hash(task_id + 工具 + 规范化参数)` |
| 3 | **检查顺序错** | 审批通过后重试又走审批分支 | 误以为"先问能不能做，再问做没做过"；实际**幂等是"是否做过"**，做过的就不需要再审批 | 顺序改为 **幂等检查 → 高危审批 → 执行** |
| 4 | **审批单没去重** | 重试产生多张一样的审批单 | 审批关在幂等关之前，且审批单自身无幂等 | 审批单按幂等键去重（`find_pending_by_key`） |
| 5 | **断言锚定文案** | 测试假失败，但功能是对的 | 断言写 `"权限" in observation`，实际文案是"无权调用" | 锚定**错误码**（`[permission_denied]`）——错误码是契约，文案会变 |
| 6 | **用例没隔离变量** | 想测"工具选错"，归因却是"权限拒绝" | 用例里同时有"无权限"和"工具选错"两个变量 | 换成有权限的角色，让工具能执行但选错 |
| 7 | **把"检出问题"当失败** | 系统正确拦住违规，却被判任务失败 | 混淆了"任务通过率"和"归因准确率" | 拆成两个独立指标 + 给用例打性质标记（`trap` / `model_error`） |
| 8 | **交替循环抓不到**（复审发现） | `A,B,A,B...` 这种循环**一路跑满 max_steps 才停**，什么都没推进却把预算烧光 | 判定条件是 `len(set(recent_calls)) == 1` —— **只要窗口里出现第二种签名，条件就永远不成立**；而且窗口只留 `threshold` 个，凑不满一个周期 | 改判**严格周期重复**（`window[i] == window[i-period]` 对全部 i 成立），窗口开到 2 倍阈值；**并补反向验证**：6 次互不相同的调用必须不被误判（判太宽松会误杀正常多步任务） |
| 9 | **动作格式没校验**（复审发现） | 模型给出 `action="query_order"`（字符串）或 `{"tool": null}` 时，**整个任务直接崩掉**（AttributeError），而不是优雅收尾 | `decision.action.get("tool", "")` 默认了 action 必然是 dict；**线索是 `FinishReason.USAGE_ERROR` 定义了却没有任何赋值路径**——一个"死枚举"说明设计时想到了这种情况、实现却漏了 | 先校验 `isinstance(action, dict) and action.get("tool")`，不合法则判 `USAGE_ERROR` 走优雅收尾；补两条用例（字符串 action / tool 为 null） |
| 10 | **参数没有下界校验**（复审发现，修坑 8 时**新引入**的） | `loop_threshold=1` → 一次**正常**调用就被判成"连续 1 次相同"，任务被误杀、**工具一次都没执行**；`loop_threshold=0` → `deque(maxlen=0)` 窗口恒空，**循环检测静默失效**，无限循环要跑满 `max_steps` 才被兜住 | 修坑 8 时把窗口改成 `2×threshold`，但没有校验下界。这两个参数配错时**不会崩，只会静默地做错事**，而且错的方向很隐蔽 | 构造时 fail-fast：`loop_threshold < 2`、`max_steps < 2`、`token_budget <= 0` 直接 `ValueError`；补 5 条断言（含"配 2 是合法的"这一正向边界） |

**其中坑 3、4 的发现过程**：坑 3 是测试场景（"审批后重试"）抓出来的；修完坑 3 才暴露出坑 4 的存在。

**坑 8、9、10 为什么值得单独说**：它们**都不是测试跑失败发现的**。
坑 8 是逐行读判定条件时，盯着 `len(set(...)) == 1` 想到"那两种签名交替呢"；
坑 9 是查"`USAGE_ERROR` 为什么定义了却搜不到赋值路径"时，顺着问出"那 action 不是 dict 会怎样"；
坑 10 更典型 —— **它是修坑 8 时新引入的**，说明"修一个边界问题"本身也会带来新的边界问题。

这类缺陷测试集里没有对应用例，就不会自己冒出来 ——
**它提醒的是"用例的盲区"和"代码的盲区"是两回事**。
修复时也刻意做了两个方向的反向验证：判太严（正常多步任务会不会被误判成循环、
下界值会不会误杀正常配置）和判太松（格式非法的动作会不会漏过去），两个方向都补了用例。

## 五、已知边界与改进方向

| 边界 | 说明 | 改进方向 |
|---|---|---|
| **审批队列在内存** | 进程重启会丢待审批任务 | 落 Postgres（真实场景必须做，因为审批可能等几小时） |
| **幂等账本在内存** | 多实例不共享 | 落 Redis（按幂等键做 SETNX + TTL） |
| **沙箱执行很简化** | 只用超时保护，无资源隔离 | Docker/gVisor 隔离 + CPU/内存配额 |
| **无确定性回放** | 轨迹已记录，但还不能"从轨迹重放" | 实现回放器（工具结果从记录读，不真实执行） |
| **评测用脚本化 brain** | 固定了模型变量，测的是系统链路 | 接真实 LLM 做端到端评测（换 brain 实现即可，评测逻辑不变） |
| **无分布式追踪** | 只有本地轨迹 | 接入 OpenTelemetry，导出到 Jaeger/Tempo |
